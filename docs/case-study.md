# Case study: from email digest to controlled report

## Context

Procurement opportunities were distributed in a recurring PDF digest. Reviewing every issue manually was repetitive and made it easy to miss a relevant notice, process the same file twice or forward an inconsistent summary.

This public project recreates the technical pattern with fictional data. It contains no production documents, tenant identifiers, recipients or company-specific rules.

## Requirements

The automation needed to:

1. notice an email whose subject contains a configurable keyword, regardless of capitalization;
2. continue only when at least one PDF attachment is present;
3. save each accepted PDF to a shared inbox;
4. wait until file synchronization has completed;
5. extract and filter the notices;
6. create a readable Word report;
7. deliver only reports generated by this process;
8. archive successful inputs and avoid creating a second artifact when the expected output already exists;
9. leave enough evidence to diagnose failures.

## Constraints

Email and SharePoint processing run in the cloud, while document parsing runs on a local machine. That creates an asynchronous boundary: a file can become visible before it is fully synchronized, and a downstream flow can notice an output before writing has completed.

The design also had to use ordinary Microsoft 365 components and a small local runtime, without requiring a custom hosted API.

## Implementation journey

### 1. Prove document generation

The first milestone was deliberately narrow: parse a representative digest and generate a DOCX with consistent headings and fields. This isolated parsing and formatting from all automation concerns.

### 2. Create a durable hand-off

Shared folders became the contract between cloud and local components:

- IN receives accepted PDFs;
- OUT receives completed reports;
- ARCHIVE stores successfully processed inputs;
- LOG records local activity.

This makes the workflow observable and allows a failed stage to be retried without restarting everything.

### 3. Make synchronization safe

The processor checks that an input is old enough to be stable, uses a lock to avoid concurrent runs and writes reports atomically. The report becomes visible under its final name only when it is complete.

### 4. Filter in layers

The email trigger uses a convenient, broad keyword. A second check inspects attachments and accepts PDFs only. At the output boundary, another rule accepts only DOCX files with the expected report prefix.

Layered filtering keeps the user-facing rule simple while preventing unrelated messages and files from progressing.

### 5. Add an output collision guard

Before report generation, the processor checks whether the expected report filename already exists. If it does, the source is archived without creating a second delivery artifact. This is intentionally a lightweight guard rather than content-hash deduplication; a source-hash registry is listed as a production-hardening step. Inputs move to the archive only after a successful result or a recognized output collision.

## Acceptance testing

| Scenario | Expected result |
|---|---|
| New matching email with one valid PDF | One PDF enters the inbox and one DOCX report is produced |
| Matching email with PDF and unrelated attachments | Only the PDF is accepted |
| Matching email without a PDF | No processing occurs |
| Input mapping to an existing report filename | No second report artifact |
| Invalid or unsupported PDF | Failure is logged and the input remains diagnosable |
| Unrelated DOCX placed in the output folder | No email is sent |
| Stale processor lock | Recovery rule allows later processing |

Automated unit tests cover the parser and filtering logic. The documented cloud-flow tests cover the integration boundaries.

## Outcome

The result is a small event-driven pipeline in which each component has one responsibility:

1. cloud acquisition selects and stores source documents;
2. the local processor creates a stable report;
3. cloud delivery validates and sends the finished artifact.

The same pattern can be reused for other recurring document digests by changing configuration and parser rules rather than rebuilding the orchestration.

## Possible next steps

- move business rules to a reviewed configuration file;
- add structured metrics and failure notifications;
- introduce a manual approval step before external delivery;
- run the processor as a managed service or container;
- add OCR for scanned documents.
